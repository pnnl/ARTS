# quicksort

*In-place recursive quicksort over EDTs — every partition step is a task,
and every task shares the same one datablock.*
Source: `third_party/ocr-apps/apps/quicksort/ocr/quicksort.c` (~220
lines). A restructured twin, `quicksort_dist.c` (sample-splitter/PSRS-style
distributed sort whose exchange is staged and whose buckets sort locally),
is registered beside it as this row's `restructured` version.

## Overview

Sorts a pseudo-randomly generated array of `u64`s **in place**, entirely
within a single shared datablock: each `qsortTask` partitions its
`[low,high]` range around a randomly-indexed pivot (Hoare partition), then
creates two child `qsortTask`s for the low/high halves — both wired to the
*same* array DB via a fresh ONCE event. Below a fixed size the range is
finished with a simple selection sort. Recursion is bracketed in an
`EDT_PROP_FINISH` scope so a single output event fires once the entire
tree (including nested finish scopes each child opens) has drained;
`finishTask` then prints the first `min(arraySize, 30)` sorted elements and
shuts down. The
array is generated by a fixed pseudo-random generator keyed only on
element index (no seed argument), so the whole run — including the exact
shape of the recursion tree — is fully deterministic for a given
`(arraySize, range)`. There is no closed-form task count (see Structure),
and — because every recursive step contends for the one shared DB (see
Wiring) — the program is a data-movement/coherence stress rather than a
compute or scheduler-width benchmark.

## Parameters

| arg | meaning | default | CLI reachability |
|-----|---------|---------|-------------------|
| `argv[1]` = `arraySize` | element count to sort | `ARRAY_SIZE` = 1000 (`#define`, used when argv is absent or 0) | ✓ parsed via `getArgc`/`getArgv` in `mainEdt` — multinode-safe (only used at DB-create/init time on rank 0, no other rank reads it directly) |
| `argv[2]` = `range` | values are `getRandNum(i) % range` | `RANGE` = 1000000 (`#define`, same fallback rule) | ✓ same path |

**Not CLI-reachable**: `CACHE_LINE_SIZE` (= 64, `#define`) sets the serial
cutoff at exactly 8 elements (`size*8 <= 64`) below which `qsortTask` falls
back to selection sort instead of recursing — this is the recursive-cutoff
threshold the brief asks about, and it is a compile-time constant with no
argv path to change it. A user cannot tune task grain without recompiling.

## Structure

Every recursive call is one `qsortTask` EDT; the recursion forms a strict
binary tree (each non-leaf node has exactly 2 children), so if `Q(N)` is
the total node count and `I(N)` the non-leaf (spawning) count,
`Q(N) = 2·I(N) + 1` exactly. There is no closed form for `Q(N)` itself:
the pivot's *index* is a size-keyed deterministic function, but the
resulting partition *sizes* depend on the generated array's values, so
tree shape depends on `range` as well as `arraySize`. Loose bounds:
`Q(N) ∈ [2⌈N/8⌉−1, ~N−7]` (balanced vs. one-element-peeled-off-per-level
worst case); a static replay of the app's own generator (this session,
not the compiled binary) gives `Q(1000)=397` and `Q(2000)=783` for the
default `range` — well above the balanced estimate, i.e. this pivot
selection (no median-of-three) skews noticeably.

| object | count | size |
|--------|-------|------|
| `qsortTask` | `Q(N)` (every node, leaf or internal) | — |
| `mainEdt` / `finishEdt` | 1 each | — |
| DBs | **exactly 1** for the whole run — the original array DB; no sub-DB is ever created | `8·arraySize` bytes |
| Events | `4·I(N) + 3` — per non-leaf node, the ONCE pair (`qsortLowDataEvt`/`qsortHighDataEvt`) plus two runtime finish events (every child `qsortTask` is created `EDT_PROP_FINISH`, and the runtime materializes a finish event per finish EDT); fixed: the root's finish and output events plus the STICKY `coordEvt` | — |
| Templates | `qsortTemplate` (reused across the whole tree, no churn) + `finishTemplate`, 1 each | — |

Worked number for the calibrated `args=[4000000, 1000000]`: DB payload =
32,000,000 bytes (32 MB); `Q(4000000)` is not computed here (data-dependent,
would need a full replay) but by the bounds above is at least ~1M and
plausibly several times that given the observed skew at smaller `N`.

Counter cross-check: verified (1 node, `1000 1000000` vs `2000 1000000`):
NUM_DB_CREATE = 2 in both runs (the one array DB plus the runtime's
constant argv block) — the single-DB claim is measured, not inferred.
NUM_EDT_CREATE 400/786 = `Q(N)+2` plus the runtime's +1 baseline, matching
the replay's `Q(1000)=397` / `Q(2000)=783` exactly; NUM_EVENT_CREATE
795/1567 = `4·I(N)+3`, confirming the finish-event accounting above.

## Wiring

The single defining fact of this app's wiring: **every** dependence on the
array DB — the root `qsortEdt` (via a post-create `ocrAddDependence`), every
recursive child (create-time depv, `DB_DEFAULT_MODE` = RW), and `finishEdt`
— is `DB_MODE_RW`, and there is only one DB. ARTS's coherence engine grants
RW to at most one holder cluster-wide at a time, so **the entire recursion
tree serializes onto a single chain of RW hand-offs** regardless of node or
worker count: a node releases (mid-body, right after partitioning, before
creating its two children) and its two children's RW requests then race for
the now-free grant — one runs, the other waits queued until the first
releases. Concurrency in the scheduler sense (many EDTs live/queued at
once) is high; concurrency in the coherence sense (RW holders at any
instant) is exactly 1. This is the sole contention point in the app — there
is no RO access anywhere (`quicksort.c:118,132-140,204`, `196`, `211`).
The two per-node "wiring" events (`qsortLowDataEvt`/`qsortHighDataEvt`) are
themselves redundant machinery — the app's own comment (`quicksort.c:141`,
`// TODO these are useless`) flags them; see notes.

## Flow

`mainEdt`: single-rank preamble — allocates the array DB, fills all
`arraySize` elements with the deterministic generator (a serial loop, no
parallelism), releases it, then wires the coordination chain (`coordEvt`,
the finish-scoped root `qsortEdt`, `finishEdt`). Execution then walks the
recursion tree, but — because of the single-DB RW exclusivity above — wall
time tracks `Q(N)` sequential ownership hand-offs, each moving/publishing
the **entire** 8·arraySize-byte array (not just the touched sub-range),
not the number of available workers. The root's `EDT_PROP_FINISH` scope
only drains once every descendant — including the nested finish scopes
each recursive call also opens — has completed; that drain fires `outEvt`
→ `coordEvt` → `finishEdt`, which RW-acquires the now-sorted array once
more (wherever it round-robin-lands) to print the first `min(arraySize, 30)`
elements.

## Placement (base)

All `ocrEdtCreate`/`ocrDbCreate` calls pass `NULL_HINT`; there is no
`OCR_APP_OPTIMIZED_PLACEMENT` layer in this source. Effective policy:

- **EDTs**: NULL hint → round-robin (`ARTS_HINT_ANY_RANK`) — `qsortTask`
  at every depth, and `finishEdt`, scatter across ranks.
- **DBs**: NULL hint → home = creating rank. The one array DB is created
  in `mainEdt`, which only ever runs on rank 0, so its home is **fixed at
  rank 0 for the entire run**.

Combined with Wiring's single-writer serialization: since execution
scatters round-robin while the DB's home stays pinned to rank 0, most RW
hand-offs cross ranks, and every hand-off moves the whole array — this is
by construction close to the worst achievable coherence traffic pattern
for an in-place sort.

## Placement (hinted)

**No `hinted` variant is offered (decision 2026-08-19).**  With one
per-node-exclusive RW block, the only thing a hint layer can do is refuse to
distribute — and that number is already on every plot, because at one node all
versions coincide: the containment performance at N nodes IS the base
1-node cell.  A horizontal line derivable from the base curve adds nothing,
so the guard code stays in the source but no `_hinted` target is built; the
restructured version carries the distribution story.

As-born combines the two worst placements this program can have (see above):
execution scatters round-robin while the single array block homes on rank 0,
so most RW hand-offs cross ranks and each one moves the whole array.

The layer (`qsHereEdtHint` in `quicksort.c`, both recursion children plus the
root and finish EDTs) pins the whole task chain to the creating rank, keeping
the block's ownership where the work is.  Like fft, this is CONTAINMENT of a
single-RW-block structure, not a scaling fix — hints cannot decompose the
array; that is the restructured version's job (`quicksort_dist`).  `pdCount <= 1` returns `NULL_HINT`
(verified: 1-node run bit-identical, sorts and shuts down cleanly).

## Sizing

`arraySize` is the only lever that changes anything about parallelism or
task count; `range` only changes which values appear (and, secondarily,
tree shape via the pivot's data-dependent split point). The serial-sort
cutoff (8 elements) is fixed at compile time, so grain cannot be tuned via
CLI. Because coherence never allows more than one RW holder cluster-wide,
**adding nodes or workers does not add measured concurrency for this
app** — extra resources sit idle waiting on the one grant. Sizing
guidance is therefore about producing enough sequential RW hand-offs and
enough cross-node whole-array transfer to be a meaningful stress, not
about feeding N×C workers:

- For a short single-node smoke run, `arraySize` in the low hundred
  thousands already produces tens of thousands of hand-offs.
- The calibrated `args=[4000000, 1000000]` (32 MB array) is sized to
  sustain a long, heavy, single-writer stream of whole-array coherence
  traffic across however many nodes are under test — larger node counts
  change *which* rank the payload has to travel to, not how much
  concurrent work exists.
